# UI Internationalization (i18n)

The MC web UI is internationalized with [next-intl](https://next-intl.dev)
(English default, German shipped). This covers the **web interface only** —
two things it deliberately does *not* cover:

- **Agent response language** is a per-agent setting (`agents.language`),
  rendered into the SOUL template as a respond-in-that-language instruction.
- **Agent templates** (SOUL/CARD/TOOLS) stay English — they are model
  instructions, not UI copy.

## Architecture

- **Cookie-based, no locale in the URL.** MC is an app behind a login;
  `/agents` stays `/agents` in every language. The active locale comes from
  the `NEXT_LOCALE` cookie (`src/i18n/request.ts`); the selector in
  **Settings → Profile → Language** writes the cookie and calls
  `router.refresh()`, so the change applies immediately.
- **Catalogs** live in `frontend-v2/messages/<locale>.json`, namespaced
  (`nav`, `settingsProfile`, …). `en.json` is the reference catalog — every
  key must exist there.
- The plugin is wired in `next.config.ts` (`createNextIntlPlugin`), the
  provider in `src/app/layout.tsx` (which also sets `<html lang>`).

## Namespaces

Catalogs are flat JSON files with one top-level key per namespace, each a
(possibly nested) object of string values. As of this writing `en.json` and
`de.json` each hold **20 namespaces, ~1,820 flattened keys**:

```
nav · settingsProfile · home · tasks · agents · inbox · sessions · shell ·
login · setup · schedule · office · vault · insights · files · settings ·
skills · repos · loops · runtimes
```

Namespaces nest (e.g. `agents.detail`, `runtimes.cliTools`,
`runtimes.modelCatalog`) — pass the dotted path to `useTranslations()` and
key lookups inside it are relative to that path.

## Adding / translating strings

Client components:

```tsx
import { useTranslations } from "next-intl";

const t = useTranslations("myNamespace");
<span>{t("myKey")}</span>
```

Nested namespace:

```tsx
const t = useTranslations("agents.detail");
<span>{t("lastSeenAgo", { ago })}</span> {/* → agents.detail.lastSeenAgo */}
```

### `{var}` interpolation

`t("key", { var: value })` substitutes `{var}` placeholders in the catalog
string, e.g. catalog value `"Archived {ago}"` + `t("archivedAgo", { ago: "3d
ago" })` → `"Archived 3d ago"`. This is the standard way to inject a
locale-aware sub-value (like the output of `timeAgo()`) into a translated
sentence — resolve the sub-value first, then hand it to `t()` as a variable,
never string-concatenate translated text.

### ICU plural — not supported by the test mock

`en.json`/`de.json` can hold real ICU MessageFormat (`{count, plural, ...}`)
for production, but **`src/test-setup.ts`'s next-intl mock does not parse
ICU plural/select** — it only does `{var}` string substitution (see below).
Where a component's test asserts a literal rendered string, use a plain
singular/plural **key pair** instead of one ICU key (e.g. `taskCountOne` /
`taskCountOther`, resolved in the component with a simple `count === 1`
check) so the mock renders the exact string a test can assert against.

### `t.rich` — one non-nested tag level only

The test mock's `t.rich()` supports exactly **one level of non-nested**
`<tag>chunk</tag>` markup, resolved against the tag-render function passed
in `values`. Nested tags (`<b>text <i>more</i></b>`) are NOT supported by
the mock and will render incorrectly under test. Prefer split keys or plain
`t()` calls over `t.rich()` in newly touched files unless you've confirmed
the component's test suite doesn't exercise the rich-rendered output.

### Shared constants: `labelKey`, never a translated string

Shared constants (see `Sidebar.tsx` for the pattern, and
`src/components/schedule/jobTemplates.ts` for a data-array variant): store a
`labelKey` (or `key`/`nameKey`/`descriptionKey`) in the constant, and
translate at the render site — **never** store a translated string in a
module-level constant, since that freezes it in one language regardless of
the active locale. `JOB_TEMPLATES` in `jobTemplates.ts` holds only
`key: "dailyStandup"`; `JobModal.tsx` resolves
`t(\`jobTemplates.${tpl.key}.name\`)` at render time.

Add the key to **both** `messages/en.json` and `messages/de.json` — a
flatten-and-compare (walk both trees, collect dotted key paths, diff the two
sets) must come back empty before committing. Catalogs are edited via
Python (`json.load`/`json.dump(..., ensure_ascii=False, indent=2)` + a
trailing newline) so diffs stay clean and German umlauts stay literal
UTF-8, not `\uXXXX` escapes.

### Union-merge for parallel catalog PRs

Multiple i18n PRs land on `main` in quick succession during a rollout wave,
each adding new keys to `en.json`/`de.json` at different points in the tree.
Conflicts on these files are almost always **additive-only** — two branches
both added new keys, neither deleted or renamed an existing one. Resolve by
taking the **union** of keys from both sides (never drop one PR's block
because it collides positionally with another's), preserving each catalog's
alphabetical/logical grouping, then re-running the flatten-and-compare parity
check across `en.json`/`de.json` before merging. If a real conflict shows up
(two PRs added *different* values under the *same* key), that's a signal the
two PRs touched the same component — resolve by picking the value that
matches the component actually shipped, not by mechanically keeping "theirs"
or "ours".

## Adding a locale

1. Create `messages/<locale>.json` (copy `en.json`, translate).
2. Add the locale to `LOCALES` in `src/i18n/request.ts`.
3. Add an `<option>` to the language selector in Settings → Profile.

## Tests

`src/test-setup.ts` mocks next-intl globally (`useTranslations`, `useLocale`
→ always `"en"`, `NextIntlClientProvider` → passthrough) and resolves keys
against the **real** `messages/en.json` — tests assert actual English labels
without mounting a provider. A key missing from the catalog resolves to the
key itself, so a label assertion fails loudly instead of passing on a
phantom string. See the ICU-plural and `t.rich` caveats above — both are
mock limitations, not next-intl limitations, and only matter for what a
*test* can assert, not for what ships to users.

Locale-aware helpers that read `useLocale()` (e.g. `timeAgo(date, locale)`
in `src/lib/utils.ts`) always see `"en"` under test, by design — this keeps
existing English-string assertions byte-identical after a helper is made
locale-aware, since the mock never exercises the German branch.

## Migration status

The infrastructure plus pattern pages (navigation, Settings → Profile)
landed first; the remaining pages were migrated incrementally in ~30 rounds.
All core pages are bilingual (20 namespaces, ~1,820 keys) as of this
writing. Known remaining gaps (call sites not reached, or files left
untouched on purpose because internationalizing them was out of scope for
the change that touched the file) are tracked in the relevant PR
descriptions rather than here — check `git log --grep i18n` for the most
recent state.

**New UI code must use `t()` from the start** — no new hardcoded UI strings.
